# Executed coverage with PB:PC and M/X

`cpu65816.CPU` can record each stepped instruction's 24-bit PC and its M/X flags through an optional set sink. Disabled recording leaves the existing harness behaviour unchanged. Hooks that return before executing an instruction contribute no instruction entry. No instruction bytes are stored.

```
python3 tools/coverage_run.py ROM /tmp/physical.json tools/validate_phys.py STATE 800
python3 tools/coverage_merge.py ROM data/coverage.json /tmp/physical.json /tmp/other.json
python3 tools/rom_map.py ROM --json /tmp/rom-map.json
```

The runner forwards the ROM and arguments to an existing harness, records successful runs and includes the original ROM hash. New traces also include harness/interpreter file hashes. A harness's own model comparisons must still be read: some existing validators print mismatch counters without a nonzero exit status. Successful process completion alone is not model validation. Generated input cases and hardware hooks remain the harness's responsibility and must be described alongside its trace.

The merged file keeps raw addresses, because ROM mirrors and executable RAM/stack kernels are different provenance. `rom_map.py` folds ROM instruction aliases into the physical bank, measures instruction lengths using the recorded M/X state and reports three disjoint tiers: executed ROM instruction bytes, additional bytes statically reached from executed ROM seeds, and additional candidate-only bytes (scan hits and unobserved documented dispatch targets). RAM entries are recorded but are not counted as extra ROM bytes. Static reachability and raw scan hits are still provisional and do not prove that code is decompiled.
